## Unresolved decision

The approved contract defines a crew session ID as the Claude subagent ID and forbids an ended session becoming live. The existing runtime deliberately supports observing resumed turns under that same Claude ID. An integration must represent these honestly without erasing earlier outcomes or claiming a fresh conversation.

The coordinator has asked whether to permit explicitly linked continuation occurrences: preserve the original Claude ID and transcript, immutable previous outcome, deterministic occurrence identity based on recorded evidence, and label the occurrence as the same conversation. No such amendment or runtime behavior is implemented here. Repeated hooks, late bookkeeping and restart must not mint duplicate occurrences; an ambiguous hook-only resume must remain explicit rather than fabricate a boundary.

## Runtime integration and linked continuations (2026-11-16)

This completes the implementation after the human approved linked continuations on 2026-11-16. It is implementation evidence for a fresh independent review. It is not acceptance.

### Contract amendment (narrow)

- `CrewSession` gains `conversation` (the Claude conversation id) and `continuation` (`{ of, via, evidence }` or null). `id` is the execution occurrence. A first occurrence has `id === conversation`, so every existing id stays valid. A continuation is `<conversation>#<n>`.
- `continueSession` records an observed resume as one new linked occurrence. The ended occurrence and its outcome are not touched. The same resume processed again returns the occurrence it already opened, live or ended. A conversation has at most one live occurrence, and it keeps its robot when that robot is free, at once or at reconcile.
- `occurrenceLabel` says `same conversation` for a continuation and `new conversation` otherwise.
- The book version stays 1. A book written before the amendment is read with `conversation = id` and `continuation = null`. `docs/crew-contract.md` carries the rules under "Linked continuations".

### Runtime (`server/pathfinder.ts`)

- The run opens the crew book on start. Workers, identified helpers and the coordinator are recorded through it. `crew.json` and `sessions.json` are no longer written; they stay frozen migration inputs.
- `addWorker` records the session and no longer pushes a team row per session. `config.team` holds the coordinator and one row per character (the session it holds now or held last). A session with no robot is listed as the plain crew bot under its role: every live one, and the latest ended one per family. This is an interim listing until 09.5 draws the overflow layout.
- The restore pass opens on every start. Reconcile runs only after the reattach window (coordinator running again, seen and stopped, or 15 s) and once the coordinator transcript is known or the window has fully passed. No snapshot and no file are published before it.
- A resume is recorded with the evidence it was seen by: a tool call id, the transcript revision it moved past, the terminal record of a turn that finished unseen, or a bare hook with no boundary.
- `OfficeSnapshot.workflow.crew` is published. Observations carry the attention Feature 06 already decided: a worker at its own open gate and the coordinator's `needs-input` are needs-you; the coordinator's `waiting` is waiting; nothing else turns pink.
- `customizeCrew` and `retireCrew` commands call the contract's write path. No Settings UI is connected (09.4).
- A crew book that can't be opened is left byte-identical. The run still observes sessions and says so in the activity feed, and shows no crew.

### Known limits

- A session that starts and ends inside the restore pass, or is first seen already ended, gets no robot (contract migration rule 5). It is listed under its role name.
- A terminal record that appears for an ended occurrence with no terminal record of its own is treated as that turn's late bytes. The runtime status re-settles as before; the book keeps the outcome it already recorded, so the two can differ until the next restart.
- A turn that both started and finished while the kitchen was down is not recorded as its own occurrence.
- A legacy saved outcome without a ticket key that the session's own report contradicts: the status shows the report (as before); the book keeps the legacy outcome.
- A bare start hook names no boundary. A second one after the continuation ended is a new resume, as the runtime already treated it.
- A helper has no Pathfinder outcome; its ended record shows "outcome unknown".
- `AgentStatus` entries stay one per conversation, in memory. A task's owner or a gate's owner can name a session whose row has moved on; its name still resolves on the server.
- Native sessions, a browser and GitHub CI were not exercised by the developer. No live kitchen state was read for writing or changed. The representative parallel-worker preview and the remaining UI belong to 09.4–09.8.


## 2026-11-16 — runtime review repair round 1 (supersedes bare-start limits above)

Independent review of `87f8e46` found four Medium runtime continuation defects. This repair waits for a fresh tool/transcript before reviving an ended worker; a bare start alone may be a delayed duplicate. A coordinator process must identify its transcript through its own hook before creating a continuation. Helpers require their own activity to resume; replacing the parent conversation ends its former helpers. Hook endings record immutable terminal-boundary metadata, so delayed or partial transcript flushes, including after restart, are consumed by the existing occurrence without inventing another or changing its outcome. The trailing blank line in crewSnapshot.ts is removed.

The old bare-start exception was not approved and is removed. The late-terminal runtime/book discrepancy described above is also removed for a hook ending with boundary metadata: late bytes preserve both recorded outcomes. Native session timing and downstream preview acceptance remain unverified.

## 2026-11-16 — runtime review repair round 2 (N1 to N5)

The re-review of `b085f0a` confirmed M1 to M4 and L1 and reported N1 to N5. The human asked for all five to be repaired. This is implementation evidence for a fresh independent review. It is not acceptance.

Round 1 told a turn's late bytes from a resume with a flag, `awaitingTerminal`, that had no way to clear when the late bytes never came. Round 2 replaces the flag's job with a count of prompt records. A turn opens with a prompt record, so a later turn is a prompt beyond the count and nothing else is. The rules are in `docs/crew-contract.md` under "How the runtime tells a turn from its own late bytes".

- N1. A pending ending no longer suppresses anything. A text-only resume after a stop hook with no terminal record, after a lost coordinator, or after a `meta.json` ending is recorded at its prompt record, including after a kitchen restart. The M2 case still holds: the pending turn's own prompt, tool records and terminal record add no occurrence.
- N2. A helper's late bytes add no prompt record, so they are not a resume. A `finished` flag older than a recorded helper resume no longer ends the resumed turn on every quiet poll. Across a kitchen restart the book says which continuation is live and how it was opened: a flag older than a live continuation ends nothing, and a tool-opened continuation whose tool record is not on disk is not ended by the earlier turn's terminal record and owes its prompt. This holds for workers too.
- N3. A pending ending keeps the tool calls its hooks showed and the transcript did not yet hold (`terminalBoundary.tools`). After a restart a replay of any of them is a replay.
- N4. A coordinator hook counts as identity only when it is handled while the process is seen running.
- N5. A fresh helper tool call is recorded when its hook arrives. A whole helper turn between two polls is one ended occurrence.

Persisted shape: `terminalBoundary` gains optional `starts` and `tools`. Books written by `87f8e46` (no boundary) and `b085f0a` (`revision` and `pending` only) load unchanged, and no ended occurrence is rewritten. The registry test covers the three shapes, and the runtime test restarts a kitchen on a book of each older shape and consumes its pending late flush.

Limits that remain, each stated in the contract: a mid-turn non-tool-result `user` record that reaches disk after the ending reads as a later turn; a tool-opened turn whose prompt never reaches disk, and none of whose tool records reach disk before its ending, leaves the count one ahead; turns that ran while the kitchen was down get no occurrence; helper tool-call memory lasts one kitchen run; an ending from before `tools` was kept does not remember hook-only tool calls across a restart; hooks carry no process identity, so a stale coordinator hook handled while a newer process already runs is taken as its own; a replayed `SubagentStop` ends whichever turn is live.

The first session of this round noted that a tool-opened continuation live at a kitchen restart, with none of its bytes on disk, was ended by the earlier turn's terminal record (and by a stale `finished` flag), so its late flush or next tool call opened a third occurrence. `b085f0a` did the same. It is the restart form of N2's stale flag and late bytes, so it is repaired here for workers and helpers, with regression scenarios.

A turn opened by a tool call is no longer owed a prompt once one of its own tool records is on disk, because records are appended in order. Without that, the first version of this round failed three existing checks in `coordinator-attention-test.ts` (R6 hook mode: a resume whose prompt was never written held the count one ahead, so the next turn's report never ended it). Only a turn's own fresh tool calls are kept for this.

## 2026-11-17 — runtime review repair round 3 (R3-1 to R3-3)

The independent review of `6552316` confirmed M1 to M4, L1 and N1 to N5. It found that counting every prompt-shaped `user` record assumed one per turn. A read-only scan of real Claude Code subagent transcripts found many such records inside a turn: system reminders after the first prompt, skill bodies, image notes, and coordinator messages and task notifications delivered mid-turn. The human chose the reviewer's rule for this round, the last automatic one. This is implementation evidence for a fresh independent review. It is not acceptance.

The rule as implemented (`subagentTurns`, `server/transcripts.ts`): a turn start is the file's first prompt-shaped record, or the first prompt-shaped record after a terminal record with no assistant record between them. A prompt-shaped record is a `user` record that is not only tool results and is not an interrupt marker. Tool results, bookkeeping records and interrupt markers between a terminal record and the prompt change nothing. A forked subagent's file opens with its inherited context, an assistant record among it, so the first prompt counts wherever it sits. Workers, helpers and restore use this one count, and the readers of the latest turn use the same prompt predicate. The contract states the rule and its limits under "How the runtime tells a turn from its own late bytes".

- R3-1. A late flush that carries mid-turn records adds no occurrence and holds no robot. This holds with the terminal record and before it, in the same run and across a restart. The same holds for a first turn's late flush that starts with a reminder. A genuine later turn, its prompt `isMeta`, is still recorded at its prompt. A whole unseen one is still one ended occurrence.
- R3-2. A helper's own mid-turn records no longer count, so the poll after its ending finds no later turn, with or without its stop hook. The order in `noteHelpers` is unchanged and now commented. A turn start the ending poll had not counted can only follow a terminal record, so it is a later turn.
- R3-3. An interrupt marker is never a prompt. An interrupt marker or a task notification after an ending with no terminal record is inside the ended turn, so it opens nothing. A task notification directly after a terminal record is a turn start under the rule. It is recorded as a resume, because real ones are answered, and its answer's terminal record ends it. An unanswered one stays live until a stop hook or the loss of its coordinator ends it.

Persisted shape: new endings write `terminalBoundary.turns`, the turn-start count. `starts` is never written again. A `6552316` book's `starts` counted mid-turn records, so it is never read as a turn count. What such an ending still owed is `starts` minus the prompt-shaped records on disk now, when that is positive. Books from `87f8e46`, `b085f0a` and `6552316` load unchanged, and no ended occurrence is rewritten. The registry test covers all four shapes and refuses an invalid `turns`. A runtime test restarts on a crafted `6552316` book whose `starts` counted a reminder and a skill body, with the late flush arriving before and after the restart. The flush adds and rewrites nothing, and the next genuine turn is recorded.

What the rule gives up, stated in the contract: after an ending with no terminal record at all (a stop hook mid-tool-call, a lost coordinator, a `meta.json` flag), a prompt has the same shape as a reminder that follows a first prompt. The rule therefore puts it inside the ended turn. A genuine resume there is recorded by its first fresh tool call. A text-only one is not recorded. This narrows round 2's N1 for that shape only. The reviewer's `probes3.ts` S3 and `probes4.ts` F6 write exactly that shape and now fail. `probes5.ts` T3 writes the same shape as a reminder and passes. No implementation can satisfy both. `crew-runtime-test.ts` N1 now checks the tool-call path and the text-only resume after a terminal record.

Real transcripts, read-only, counts only, nothing copied: on 159 Claude Code subagent transcripts, `subagentTurns` agrees with the reviewer's classification in all 159 files. That is 189 turns, 25 multi-turn files and 383 prompt-shaped records. Its legacy count equals the `6552316` count in all 159. The first scan disagreed on 4 forked-subagent files, whose first prompt follows an inherited assistant record. That led to the fork clause above.
