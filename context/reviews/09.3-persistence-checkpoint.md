## Unresolved decision

The approved contract defines a crew session ID as the Claude subagent ID and forbids an ended session becoming live. The existing runtime deliberately supports observing resumed turns under that same Claude ID. An integration must represent these honestly without erasing earlier outcomes or claiming a fresh conversation.

The coordinator has asked whether to permit explicitly linked continuation occurrences: preserve the original Claude ID and transcript, immutable previous outcome, deterministic occurrence identity based on recorded evidence, and label the occurrence as the same conversation. No such amendment or runtime behavior is implemented here. Repeated hooks, late bookkeeping and restart must not mint duplicate occurrences; an ambiguous hook-only resume must remain explicit rather than fabricate a boundary.

## Runtime integration and linked continuations (2026-11-16)

This completes the implementation after the human approved linked continuations on 2026-11-16. It is implementation evidence for a fresh independent review. It is not acceptance.

### Contract amendment (narrow)

- `CrewSession` gains `conversation` (the Claude conversation id) and `continuation` (`{ of, via, evidence }` or null). `id` is the execution occurrence. A first occurrence has `id === conversation`, so every existing id stays valid. A continuation is `<conversation>#<n>`.
- `continueSession` records an observed resume as one new linked occurrence. The ended occurrence and its outcome are not touched. The same resume processed again returns the occurrence it already opened, live or ended. A conversation has at most one live occurrence, and it keeps its robot when that robot is free, at once or at reconcile.
- `occurrenceLabel` says `same conversation` for a continuation and `new conversation` otherwise.
- The book version stays 1. A book written before the amendment is read with `conversation = id` and `continuation = null`. `docs/crew-contract.md` carries the rules under "Linked continuations".

### Runtime (`server/pathfinder.ts`)

- The run opens the crew book on start. Workers, identified helpers and the coordinator are recorded through it. `crew.json` and `sessions.json` are no longer written; they stay frozen migration inputs.
- `addWorker` records the session and no longer pushes a team row per session. `config.team` holds the coordinator and one row per character (the session it holds now or held last). A session with no robot is listed as the plain crew bot under its role: every live one, and the latest ended one per family. This is an interim listing until 09.5 draws the overflow layout.
- The restore pass opens on every start. Reconcile runs only after the reattach window (coordinator running again, seen and stopped, or 15 s) and once the coordinator transcript is known or the window has fully passed. No snapshot and no file are published before it.
- A resume is recorded with the evidence it was seen by: a tool call id, the transcript revision it moved past, the terminal record of a turn that finished unseen, or a bare hook with no boundary.
- `OfficeSnapshot.workflow.crew` is published. Observations carry the attention Feature 06 already decided: a worker at its own open gate and the coordinator's `needs-input` are needs-you; the coordinator's `waiting` is waiting; nothing else turns pink.
- `customizeCrew` and `retireCrew` commands call the contract's write path. No Settings UI is connected (09.4).
- A crew book that can't be opened is left byte-identical. The run still observes sessions and says so in the activity feed, and shows no crew.

### Known limits

- A session that starts and ends inside the restore pass, or is first seen already ended, gets no robot (contract migration rule 5). It is listed under its role name.
- A terminal record that appears for an ended occurrence with no terminal record of its own is treated as that turn's late bytes. The runtime status re-settles as before; the book keeps the outcome it already recorded, so the two can differ until the next restart.
- A turn that both started and finished while the kitchen was down is not recorded as its own occurrence.
- A legacy saved outcome without a ticket key that the session's own report contradicts: the status shows the report (as before); the book keeps the legacy outcome.
- A bare start hook names no boundary. A second one after the continuation ended is a new resume, as the runtime already treated it.
- A helper has no Pathfinder outcome; its ended record shows "outcome unknown".
- `AgentStatus` entries stay one per conversation, in memory. A task's owner or a gate's owner can name a session whose row has moved on; its name still resolves on the server.
- Native sessions, a browser and GitHub CI were not exercised by the developer. No live kitchen state was read for writing or changed. The representative parallel-worker preview and the remaining UI belong to 09.4–09.8.


## 2026-11-16 — runtime review repair round 1 (supersedes bare-start limits above)

Independent review of `87f8e46` found four Medium runtime continuation defects. This repair waits for a fresh tool/transcript before reviving an ended worker; a bare start alone may be a delayed duplicate. A coordinator process must identify its transcript through its own hook before creating a continuation. Helpers require their own activity to resume; replacing the parent conversation ends its former helpers. Hook endings record immutable terminal-boundary metadata, so delayed or partial transcript flushes, including after restart, are consumed by the existing occurrence without inventing another or changing its outcome. The trailing blank line in crewSnapshot.ts is removed.

The old bare-start exception was not approved and is removed. The late-terminal runtime/book discrepancy described above is also removed for a hook ending with boundary metadata: late bytes preserve both recorded outcomes. Native session timing and downstream preview acceptance remain unverified.
