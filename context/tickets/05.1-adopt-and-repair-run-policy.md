- Decision (developer, review round 1, 2026-11-11) [superseded, see above]: github-dev is an allow-list over parsed Bash
  text, not a deny-list over a string. The command is lexed (quotes, escapes, $…, $(…), backticks,
  heredocs, redirections); every git and gh command in it, also under sh -c, eval, find -exec and
  known wrappers, must match a recognised shape: gh writes carry exactly `-R <repo>` and only the
  flags listed per command (written `-x value` or `--long=value`), pushes take only `-u -q -v -n
  --porcelain --no-verify --progress`, git subcommands must be local built-ins from a fixed list
  (or aliases resolving to one), without their command-running options. Anything else, and any
  program name or git/gh argument the shell computes, is refused. Why: every bypass in round 1
  was a shape the deny-list hadn't imagined; an allow-list fails closed on shapes it doesn't know,
  and its claim ("these shapes, nothing else") can be stated and tested.
- Decision [superseded, see above]: the guard file is hash-checked on every call. The hook command reads the guard once,
  compares its SHA-256 with the hash fixed at coordinator start, and runs those bytes from memory,
  so a changed or emptied guard blocks every guarded call (B1) without a check-then-run race.
  github-dev in run-policy.json is honoured at coordinator start only when it names the project's
  origin. Bash can still rewrite these files (stated in POLICY_LIMITS); the text check on their
  names is kept as a speed bump and described as one.
- Stated, not closed [superseded, see above]: github-dev is not a sandbox. Scripts, interpreters (node -e, python -c),
  HTTP clients, git hooks and git/gh config that runs programs are bounded only by the GitHub

  unchanged (the 7b3eda3 regex, compared against the 7b3eda3 guard script in the test); its one
