## Goal

After a verified merge, the kitchen reconciles the main checkout without losing anything, completes the ticket through Pathfinder, releases the claim, and refreshes the dispatch plan. The board then shows the ticket as integrated.

## Context

- Read: Feature 10, `skills/ticket/actions/complete.md`, `skills/orchestrate/actions/integrate.md` steps 7-9, `skills/orchestrate/engine/integration.mjs` (`releaseClaim`), `PathfinderRun.answerGate` (`server/pathfinder.ts:901`, read only).
- Relevant area: `server/delivery/reconcile.ts`, `server/delivery/handback.ts`, `src/ui/drawers/DeliveryDrawer.tsx`

## Changes

- `reconcile`, on the human's click:
  - list main's tracked modifications and untracked files that collide with `origin/main`;
  - verify each against the merged content and the backup;
  - move them to `~/.controlroom/<kitchen>/backups/<ts>/` with a manifest, never deleting;
  - fast-forward main only.
- `handback`: type one marked request to the coordinator to run `/ticket complete <key>` and `orchestrate release <key>`, idempotent by marker. Never re-send on dismissal (see Feature 06's notes on repeated messages).
- Refresh with `orchestrate plan --json` and show the newly eligible tickets.
- Completion records follow Feature 10's Notes / Decisions (default: a records PR through the same flow).

  - release is refused until local main contains the merge.

Decision:

> Human approves the separate ticket/<key>-records branch approach. Mechanical verification restricts the diff to the intended ticket Status, derived Feature Status and the completion-history entry; any other change requires normal review. The human's exact in-app approval can accept that constrained records diff. Never mark completion before verifying the implementation landed on main, and never create records PRs for records PRs. Resume the existing work without asking again.

- Implemented after the gate (2026-11-13), the records PR as decided:
  - **Records delivery.** `server/delivery/records.ts` derives exactly what `/ticket complete` writes (the ticket's `## Status` → Complete; the Feature's `## Status` → Complete only when every other ticket of the Feature is done; one `context/history.md` entry only when the Feature completes), writes it as one commit cut from the updated local main, and checks any records head mechanically: one commit, its parent contains the verified implementation merge and is on origin's main, and it changes exactly those files to exactly those bytes and modes, both against its parent and as it would land on origin's current main. Anything else is refused as needing normal review. It is delivered by a second `Delivery` (same class, `records` config) with its own state file (`<key>.records.json`), approval and steps: the same exact-head approval, push refspec, PR, checks, acknowledgement, pinned squash merge, verification and reconcile as a ticket. The records track has no records, handback or plan of its own, and `prepareRecords` takes no `track`.
  - **Order (forced by the engine, not chosen).** Reconcile main → hand back (`/ticket complete`, `orchestrate release`) → claim released → prepare and deliver the records → reconcile again. `orchestrate release` proves a squash merge by merging the ticket branch into local main and requiring no change; once the records commit (which rewrites the ticket's Status line the branch also wrote) is on local main, that merge conflicts and release needs `--force`. So `prepareRecords` is refused, on the server, until the engine reports no claim for the ticket (`owner <key> --json`), and the handback tells the coordinator the kitchen delivers the records and not to edit, commit or push them. `scripts/delivery-after-merge-test.ts` shows both orders against the real engine.
  - **No local branch.** `ticket/<key>-records` is the branch on origin (the PR's head). Locally the commit is kept under `refs/tin-and-thyme/records/<key>`, created once and never moved: the engine reads every local `ticket/<key>-*` branch as a claim on that ticket (`claims.mjs`), so a local records branch would show each delivered ticket as a stale, orphaned claim in `status` and in every `plan`. The ref is never pushed (the only push is `<sha>:refs/heads/ticket/<key>-records`).
  - **Feature status reads the store.** The store (the main checkout's `context/tickets/`) can hold tickets main does not track yet. The Feature completes only when its other tickets are done both in the commit and in the engine's `board --json`; if the board cannot be read, nothing is prepared.
  - **Bytes.** A ticket, Feature or history file that does not read back to the same blob (not plain UTF-8) is refused rather than rewritten.
- Reconcile repairs found while taking this over:
  - paths are passed to git as literal pathspecs: a colliding `docs/[ab].md` or `app/[id]/page.tsx` was a pattern, and `git checkout <head> -- <path>` also reverted unrelated edited files it matched, with no backup;
  - a new file staged and then edited again (`AM`) could not be unstaged (`git rm --cached` refused), after tracked files had already been moved;
  - when git refuses the fast-forward (or the move) after files were moved, every moved file is put back from its verified copy, the index entries of those paths are restored, and the listing is taken again to confirm it is the one shown; the backup folder is kept either way, with the manifest saying which happened.
