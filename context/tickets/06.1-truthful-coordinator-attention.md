# Truthful coordinator attention and review-session outcomes

## Status

In Progress

## Parent Feature

`06-coordinator-attention-state.md`

## Blocked by

None

## Goal

The coordinator shows "Needs you" only for a real unresolved gate, permission request or question, and "waiting on workers" when its turn ended while dispatched workers are live. Review sessions that reported are not labelled Interrupted.

## Context

- Read: Feature 06 (code locations); `docs/crew-contract.md`, once 09.1 lands, for the state names
- Relevant area: `server/pathfinder.ts`, `server/transcripts.ts`

## Changes

- Make the Stop-hook and transcript-poll paths aware of live workers, open gates and pending permission prompts.
- Classify review-session endings from their PASS/FINDINGS/GATE report.
- Expose a `waiting` coordinator state that the UI can render.
- Worker-to-ticket attribution (human-approved 2026-11-12, prioritized). Replace the FIFO `pendingBriefs` matching (`server/pathfinder.ts:395/410/636` at `7b3eda3`) so that:
  - a queued brief is consumed exactly once;
  - concurrent starts arriving in any order map correctly;
  - helpers never inherit a ticket, stage or gate;
  - resumed and finished sessions never keep another session's identity;
  - reconnect and restart rebuild identities from the transcripts;
  - an attribution that can't be established stays unknown and is shown as unknown, never guessed.

  Prefer exact identifiers (the subagent id from the Agent tool result, `tool_use_id`, the brief's worktree and key). Never rely on name, role or queue position alone.

## Verification

- Unit tests with fixture transcripts: turn ended with live workers → waiting; an open gate → needs-you even while workers run; no workers and a question → needs-you; a review session that reported → not interrupted.
- Attribution tests: `PostToolUse` before `SubagentStart`; two concurrent dispatches answered in reverse order; a helper started while a brief is pending; a resumed session on the same ticket; a finished session followed by a new one; restart and reconnect reconstruction from transcripts; and an ambiguous case that stays unknown.
- `pnpm typecheck` and `pnpm build` pass.

## Out of Scope

- Repair round 4 (2026-11-13, after review 4 FINDINGS on `7a84e8a0`; human gate decisions under `eaa2721c8187` and `95aa5f63af07` below; built on 06.3's engine and merged with `origin/main` `feb7bd5`):
  - Source of truth. On every start-up, refresh and answer the kitchen reads Pathfinder's durable gate record (`server/gateRecord.ts`, `gateNow` in `server/pathfinder.ts`): the open gate's occurrence from the state file's `Gate-Id`, and the resolved occurrences from the gate notes in the claim's ticket file. It writes nothing to the project.
  - Checked first, against the real engine (the `record:` checks): a new opening gets a new occurrence; a retry reuses it; a resolution, or a close by a state change, names it; the identical question opened again gets a different one; a hand-set gate and the old three-fact notes have none.
  - One request per occurrence. A request's revision is its occurrence (`<key>#<occurrence>`). The identical question opened again is a new request: no answer, snooze or owner is carried over. A retried opening is the same request. A delivered answer is kept by occurrence in `~/.controlroom/<slug>/gate-answers.json`, so a restart shows the same result and sends nothing twice.
  - Attribution. A session's GATE report is saved with the occurrence it was made in (`occurrence` in `sessions.json`, replacing `consumed`) and credits that occurrence only, so a resolved occurrence retires it for good. The occurrence is recorded only when all of this holds: the kitchen saw it open at a hook event from the session itself; it is still the open one when the session stops; the report states its question. A report that repeats the question already saved for that session is never moved to a later occurrence. No clock is read.
  - Answers. `answerGate` reads the record again before it types anything. It refuses an answer that names another request, names none, or is for an occurrence the record shows resolved, closed or replaced, including between two polls. A refusal never replaces an answer already delivered for the open occurrence. The message typed into the coordinator names the occurrence.
  - No occurrence (a hand-set gate, a kit from before 06.3, an old `sessions.json` entry): the owner is unknown, with a diagnostic. The gate stays answerable, also after an earlier answer ("Send another answer"). After a restart it is asked afresh, because nothing shows it is the same gate.
  - The history wins over the state file: an occurrence the notes record resolved is not an open request, even while the state file still shows it.
  - This closes round 3's known limit (a resolution the kitchen didn't see).
  - **Consequence for the standard flow, for the reviewer and the human to weigh.** The worker brief tells a worker to set its gate by hand, and the coordinator runs `gate open` afterwards. The report is therefore made before the occurrence exists, and the request shows "Unable to identify session"; its diagnostic names the session that reported the same question. A session is credited when the occurrence was already open while it ran: it opened its gate through the engine (`orchestrate state <key> --set human-gate --gate …`), or it re-raised a gate that was open. Crediting a report to the first occurrence opened afterwards for the same words was left out on purpose. The record can't tell that from a hand-set gate that a state change closed (the engine writes no note for a gate with no `Gate-Id`) and that was then raised again.
  - Limits:
    - On a GitHub Issues store the gate notes are issue comments, which the kitchen doesn't read. Identity still comes from `Gate-Id`; only the "history says resolved" check is missing there.
    - The engine's `gate resolve` takes no occurrence. Once an answer is typed into the coordinator, only the coordinator can keep it from a later occurrence; the kitchen refuses to send for anything but the occurrence open at that moment.
    - "Recorded" still means the engine stopped reporting the gate, as before.
    - 09.3 replaces `sessions.json`; it must keep `occurrence`, or no session is credited.
  - Tests: `scripts/coordinator-attention-test.ts` has 324 checks (222 before). The round-4 sections run this repository's engine on scratch projects with real claims. 57 of them fail on the code before this round. Each rule was also checked by breaking it and seeing a test fail.
