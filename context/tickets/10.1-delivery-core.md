# Delivery core: validated server-side delivery operations

## Status

In Progress

## Goal

A server-only module performs ticket delivery as explicit, validated, idempotent operations: inspect, push, ensure-PR, status, merge, verify. Their state is persisted per ticket. Nothing is wired to the UI yet.

- Relevant area: `server/delivery/ops.ts`, `server/delivery/state.ts`, `server/delivery/forge.ts`, `scripts/delivery-test.ts`

## Changes

- `server/delivery/ops.ts`: typed operations over an injectable runner (`execFile`, fixed argument vectors, no shell):
  - `inspect(key)`: validates origin `owner/name`, the claim, the branch pattern, a clean worktree, the reviewed head plus record-only commits, the ancestry denylist, a diff secret scan, the fetched `origin/main`, and the expected merge tree.
  - `push(key, head)`: pinned refspec only, never forced. An identical remote head is OK; a different one is refused.
  - `ensurePr(key)`: reuse an open PR or create one (not a draft).
  - `status(key)`: head, checks (an empty list means "none reported"), mergeable, review decision.
  - `merge(key, approval)`: squash with `--match-head-commit`, refuses a stale approval, and is idempotent when the PR is already merged.
  - `verify(key)`: the new `main` has the expected parent and tree.
- `server/delivery/state.ts`: per-ticket state with step results, in `~/.controlroom/<kitchen>/deliveries/<key>.json`. Approval records `{head, base, tree}`. Token-shaped text is redacted from every stored or returned message.
- `server/delivery/forge.ts`: the `gh` calls for PRs, checks and merge, reusing `server/github.ts` where it fits.
- `scripts/delivery-test.ts`: fake-runner tests.

**Repair round 1** (fresh developer, 2026-11-12) on review 1 FINDINGS of `ef1abb95`; every High, Medium and Low finding except L4 (10.2 shows the evidence):
- H1 (orchestrator decision, Feature 10 Notes): the reviewed head is accepted only from a `Last:` line that is exactly `review PASS on <full 40-hex sha>`. Short ids, lower-case "pass", and extra wording (FINDINGS, FAIL, "not", a round number) are refused. The 05.1 → 05.2 replay fixtures use the real rewritten lines.
- M1: the claim's record (`Store:`) must match `^context/tickets/<key>-[^/]+\.md$`, or inspect refuses. Post-review commits may change only that file.
- M2: `git remote get-url --push --all origin` must return exactly one URL, and it must be the configured repository. This applies `pushurl` and `pushInsteadOf`.
- M3: a PR whose `isCrossRepository` is not false, or whose `headRepositoryOwner` is not the repository owner, is refused in `findPr` (open or merged) and in `viewPr`. A closed fork PR is ignored.
- M4: `merge` holds `merge.lock` in the deliveries folder. The lock is shared by every Delivery instance and kitchen process, and it covers the PR re-read, the pre-merge re-inspection, the merge and its verification. Immediately before merging, `ls-remote origin refs/heads/<base>` must equal the approved base; otherwise the approval is invalidated as stale.
- M5: as soon as GitHub reports the PR merged, the state records `merged: {at, pr, commit}`, `mergeCommit`, and `verified: false`, before verification runs. A verification failure reports "merged … but NOT verified", and a retry never merges again.
- M6: denylist entries must be 7–40 lowercase hex digits, or they are refused before reaching git (so `-…` never reaches git). An abbreviation must resolve to exactly one commit; a missing or ambiguous one is refused.
- M7: the scan reads every commit's patch in `mergeBase..head` (`git log -p`, merges against their first parent; needs git ≥ 2.31) and every commit message. A secret that was added and later removed is refused.
- L1: `---`/`+++` count as headers only between `diff --git` and the first hunk. Binary files are listed in `Inspection.unscanned` and in the inspect message.
- L2: `exec.run` takes an optional `env` that is added to the server's environment. Delivery's `git` and `gh` calls (`defaultRunner`) set `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`, `GH_PROMPT_DISABLED=1` and `GIT_SSH_COMMAND=ssh -o BatchMode=yes`. A missing credential then fails at once instead of waiting on a prompt the kitchen's terminal could otherwise receive. If the human already exports `GIT_SSH_COMMAND`, it keeps its options and gains BatchMode. A `GIT_SSH` program is left alone. A `core.sshCommand` setting is overridden by the env var, which is a known limitation. Other `run` callers are unchanged.
- L3: checks that are all "skipping" summarize as "none", never "passed".
- L5: the deliveries folder is set to 0700 even when it already exists. Temp files get unique names (pid plus random) and are created exclusively. A step first checks that the state is readable, so a corrupt file returns a `failed` Outcome with nothing run; a failure to record also returns an Outcome.
- L6: the in-memory `busy` set is replaced by a per-ticket `<key>.lock`, which is cross-instance and 0600. A lock whose holder process is gone is reclaimed.
- Known limit: two processes reclaiming the same crashed lock at the same instant could both proceed. The window is narrowed by re-reading the lock before unlinking it.
- Tests: `scripts/delivery-test.ts` has 436 checks, up from 225, and the 05.1 → 05.2 replay runs on the real objects. **Repair round 2** (fresh developer, 2026-11-12) on review 2 FINDINGS of `046161d6`, N1 and N2 only, per the gate decision above:
- N1: `merged` is now a `MergeRecord` `{at, pr, commit, approval, verification}`. When GitHub first reports the merge, the record stores the approval the merge was made under (head, base, tree, at), and later reports only fill in a missing merge commit. `verify`, the already-merged path and every merge retry check against that stored approval, never the caller's or the current one. `inspect` still invalidates `approval`, which is only the permission for a new operation, and never touches `merged`. Once a merge is recorded, `merge` never runs the merge command again, whatever approval it is given; it re-verifies instead. A failed verification can be retried with `verify` or `merge`. A verified merge stays verified: a later failing re-check is reported ("stays verified; this re-check failed") and does not flip it.
- N2: before the command is sent, `pendingMerge` `{at, pr, approval, status, note}` is written, so an interrupted merge is never read as "not merged". After a successful command, the PR is re-read (`confirmDelaysMs`, default 500 ms then 1500 ms). If GitHub still does not report MERGED, the merge is recorded as `confirmation-pending` and the step fails as `blocked`. A failed command that GitHub does not confirm is recorded as `unknown`. Before any new merge attempt, and in `verify`, a pending merge is reconciled with reads only: the PR is re-read, then `ls-remote` checks origin's base, then the code checks whether the approved head or tree is now on it. The result is merged (recorded under the pending approval, then verified) or not merged (GitHub does not report it, and origin's base is still the approved base or has neither the approved head nor the tree), and the pending record is cleared. Anything else stays pending, and nothing is merged.
- Tests: `scripts/delivery-test.ts` has 573 checks, up from 436. New tests cover repeated inspects and verifies before and after the merge; merges with the fresh, original and different-base approvals, which never merge again; a verification failure (fetch) that recovers with no second merge; a verified re-check failure that does not flip; GitHub reporting OPEN after a successful merge, then failing to read, then MERGED; failing re-reads, then a retry carrying another approval; a badly reported merge, with and without lag; a refused merge settled as not merged and merged once on retry; and an interrupted merge, landed or not, after a restart. Restart persistence uses a fresh `Delivery` and store, and the original approval and its `at` are checked throughout.

**Repair round 3** (fresh developer, 2026-11-12) on review 3 FINDINGS of `ec1d7a3b`, F1 to F3 only, per the gate decision above. The repair changes only `server/delivery/{state,forge,ops}.ts` and `scripts/delivery-test.ts`:
- **Four outcomes, kept apart.** `mergeOutcome(state)` in `state.ts` returns one of these, or `none` when no merge was attempted:
  - `pending`: the command exited 0 and GitHub has not confirmed the merge (`pendingMerge.status` is `confirmation-pending`);
  - `unknown`: the command was `sent` and interrupted, failed `unknown` (unclearly), or was `refused` but is not yet settled;
  - `merged`: GitHub reports the PR merged;
  - `not-merged`: confirmed not merged on positive evidence, kept in the new `lastAttempt` `{at, pr, approval, outcome, settledAt, reason}`.

  The pending approval and its `at` stay in `pendingMerge` until the outcome is confirmed. When an attempt is confirmed not merged, its approval moves to `lastAttempt` and is kept. Only read-only reconciliation runs before any new attempt: the PR is re-read, `ls-remote` checks the base, and the approved head or tree is looked for on main.
- **F1.**
  - A failed merge command is classified by `isClearMergeRefusal` (forge.ts):
    - GitHub's explicit refusal text (head or base branch modified, not mergeable, required checks or reviews, rule violations, …) is a clear refusal.
    - So is a refused sign-in.
    - Anything that looks like a timeout, kill, signal, 5xx, network error, rate limit, or unrecognized text is unclear.
  - A clear refusal is recorded as `refused`. Once GitHub and origin show that nothing landed, it settles as not merged at once.
  - An unclear failure is recorded as `unknown`. It is settled as not merged only once `settleAfterMs` has passed since the command was sent. That delay defaults to 5 minutes and must be longer than the merge timeout, `MERGE_TIMEOUT_MS` (60 s), or the constructor refuses it. GitHub must still not report the PR merged, and origin must have neither the approved head nor the tree.
  - A closed PR is also positive evidence that the merge did not happen.
  - Until settled, the merge is held as `blocked`, and no new merge command is sent. If the merge lands late, it is recorded and verified under the original pending approval. If it lands after the attempt was settled as not merged, verification still binds the original approval from `lastAttempt`.
- **F2.**
  - A merge made outside the app (none sent and none pending) is recorded with `merged.approval: null`, as merged-unverified.
  - `verifyRecorded` tries these approvals, de-duplicated, and binds the first that verifies (parent = base, tree = tree, on main), never any other:
    - `lastAttempt`'s approval;
    - the invalidated approval;
    - the current approval;
    - an approval the `merge` caller offers, including when the merge is already recorded.
  - A wrong or post-merge approval is never kept, so the correct one can still verify the merge later.
  - A merge this app sent is still bound at once to the approval it was sent under, as N1 requires.
  - A bound approval is never replaced, and a verified merge never flips.
- **F3.** `reconcile` respects `confirmation-pending`. It never settles it as not merged by time, however long after (the tests advance the clock a week). Only these settle it:
  - GitHub reporting MERGED;
  - the PR closed;
  - the approved head or tree on main, which keeps it pending until GitHub reports the merge.
- **Test change.** One existing scenario (`n2-interrupted-not-merged`) encoded F1: it settled an interrupted merge immediately. Its check is unchanged, but it now runs after the settle delay, with an injected clock. New checks show that the merge stays unknown, with its approval, before that.
